In our team we have something called technical lunches.

It’s a low-key format where someone presents a small topic, pattern, or tool they’ve been working with. Nothing fancy, just sharing knowledge across the team.

I’m fairly new in the team, so this was a good opportunity to both learn something properly and contribute a bit early on.

Topic: MDC (Mapped Diagnostic Context)

The topic I picked was MDC — a simple but very useful feature in logging frameworks like SLF4J that I had been annoyed at beeing almost completly abscent from all our code bases.

It lets you attach contextual information to your logs, for example:

  • saksid
  • jobbId
  • request identifiers

This makes logs much easier to understand and filter, especially in distributed systems.

The Problem

MDC is stored per thread, which means:

  • You have to remember to clean it up
  • It does not automatically follow when switching threads

Forgetting cleanup can lead to confusing logs where context "leaks" between operations.

Approaches

I walked through a few different ways of handling MDC:

  • Manual MDC.put() / MDC.remove()
  • MDC.putCloseable() with try-with-resources
  • @Cleanup from Lombok to reduce indentation
  • A small utility using a Map to set multiple values at once

The goal was to make usage safer and less noisy.

Threads

One important detail is that MDC is thread-local.

If you start a new thread, the context is not there unless you copy it manually.

That’s easy to forget, and can explain why logs suddenly lose context.

Takeaway

MDC is simple, but small mistakes can lead to subtle bugs in logging.

A bit of structure around how it’s used goes a long way:

  • Always clean up
  • Prefer scoped usage (AutoCloseable)
  • Be aware of thread boundaries
